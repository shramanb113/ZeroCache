## What Zerocache is

A standalone, Rust-native embedding cache that sits between an application's ingestion pipeline and its embedding provider (OpenAI-compatible endpoint). It intercepts `/v1/embeddings` requests, serves previously-computed vectors from a local content-addressed store, and forwards only cache misses upstream. Adoption requires no SDK — a consumer just points its existing OpenAI-compatible embedding client at Zerocache's `base_url`.

First validation consumer: Argus (Mastra/TS + pgvector). A second, Python-based consumer (LangChain/LlamaIndex) is required before the "any framework" neutrality claim is considered proven, not just asserted (PRD §5, §14, §15).

## Architecture — layered, dependencies point inward only

This is a hard, structurally-enforced rule (via Cargo workspace crate boundaries, not convention): outer layers know about inner layers; inner layers never know outer layers exist.

| Layer | Responsibility | Depends on | Knows about I/O? |
| --- | --- | --- | --- |
| Core (domain) | Cache key derivation, hit/miss reconciliation | nothing | No |
| Ports | Trait contracts for storage, provider, wire-shape access | Core | No (traits only) |
| Application | Orchestrates end-to-end cache flow via ports | Core, Ports | No (works through traits) |
| Adapters | Concrete implementations of ports | Ports | Yes |
| Interface/Transport | HTTP surface, wire-shape translation, response shaping | Application | Yes |

### Core (domain)

Pure logic — no async runtime, no network, no disk access, nothing from `tokio`/`axum`/any storage crate.

- `CacheKey = blake3(model_id + model_version + text)`. Model identity is included deliberately so a model/version upgrade can't silently return a stale-but-plausible vector.
- Hit/miss reconciliation: given a batch of keys and lookup results, determine hits vs. misses while preserving original input ordering.
- Core has zero awareness of which framework/language sent the request — that's resolved entirely at the transport layer before anything reaches core. This is what makes "any framework" an architectural property, not a marketing claim.

### Ports

Trait contracts that core/application depend on but never implement directly — this differs from the PRD §6.2 snippet, see "Deviations" below; check `zerocache-ports/src/lib.rs` directly for the current trait definitions rather than trusting a snippet here, which would just go stale the next time the trait changes (it already had, missing `EmbeddingStore::delete`, until this note replaced it).

`EmbeddingProvider` is async (2026-07-24) — adapters use async `reqwest`, not `reqwest::blocking`, so a provider call is `.await`ed directly in `zerocache-http` rather than needing `tokio::task::spawn_blocking`. `EmbeddingStore` stays synchronous (`sled`/`redis` are blocking APIs); their calls still run inside `spawn_blocking`. `version()` replaces the old global `model_version: String` on `AppState` — each adapter returns its own `env!("CARGO_PKG_VERSION")`, so the cache key's version component is tied to that adapter crate's own `Cargo.toml` version, not a manually-maintained string someone has to remember to bump. Each adapter also chunks its input into batches of `MAX_BATCH_SIZE = 100` — a single conservative constant, not tuned per-provider, since the real per-provider limits couldn't be reliably verified.

### Application

Runs the actual cache flow against the two ports: split batch into hits/misses, call the provider port for misses only, write results back through the store port, reassemble the final ordered response. Fully testable with mock ports — no real network/disk required. Also unaware of wire shape; that translation happens once, at the transport boundary.

### Adapters

Swappable concrete implementations, each independent:

- `EmbeddingStore`: two implementations exist. `zerocache-adapters-sled` (embedded, raw fp32, no compression, no eviction — content-addressed keys mean a hit is valid indefinitely, so eviction is a capacity concern only, never a correctness one) for local dev / single-instance. `zerocache-adapters-redis` (pooled via r2d2, no mutex, no distributed lock — content-addressing means two replicas racing to fill the same key both compute the same value, so a last-write-wins `SET` is safe) for multi-replica/Kubernetes deployments. Selected at startup via `ZEROCACHE_STORAGE_BACKEND=sled|redis`.
- `EmbeddingProvider`: v1 = single OpenAI-compatible adapter. Future adapters (separate crates, no change to core/ports/application): Mistral, Gemini, Voyage AI, Cohere.

Adapters depend inward on port traits only — adding a new adapter never touches core or application.

### Interface/Transport

Two deliberately separate responsibilities:

- **Wire-shape translation**: parse the incoming request (v1: OpenAI `/v1/embeddings` shape — TS and Python frameworks alike default their embedding clients to it) into the transport-agnostic internal request format.
- **HTTP surface**: an axum server handling concurrent requests from multiple independent consumers.

Keeping these separate is what lets a second wire shape be added later as just a new translation function, invisible to application/core.

## Deviations from the PRD

The PRD (§3) is authoritative for intent, but treat these as the actual code, not what the literal PRD text says:

1. **`EmbeddingProvider::embed_batch` takes a `model: &str` parameter.** PRD §6.2's snippet omits it, but the wire contract (§10) requires honoring whatever `model` the client sends per-request — without it, one adapter instance could only ever serve a single hardcoded model.
2. **`EmbeddingStore`/`EmbeddingProvider` carry `Send + Sync` bounds**, needed because `zerocache-http` shares them across async axum handlers behind `Arc<dyn Trait>`.
3. **Both traits return `Result`, not bare values.** Originally scaffolded without this (matching PRD §6.2 literally) and it was a real gap — failures panicked instead of surfacing as HTTP errors. Fixed 2026-07-23.
4. **`zerocache-adapters-redis` exists in v1.** PRD §4 and §6.4 explicitly defer distributed/multi-instance storage to "Future" work. Added ahead of that schedule because Kubernetes multi-replica deployment is a real near-term requirement, not a hypothetical — confirmed with the PRD's author before building. `zerocache-adapters-sled` remains the default; Redis is opt-in via `ZEROCACHE_STORAGE_BACKEND=redis`. An optional `ZEROCACHE_TTL_SECONDS` (unset by default, meaning entries never expire) sets a per-store-instance expiry: Redis uses native `SET...EX`, sled stores an 8-byte expiry-timestamp prefix ahead of each vector and checks it lazily on read. `0` or an unparseable value is treated as unset (with a startup warning), since `0` behaves inconsistently between backends (Redis rejects it, sled would treat it as instant-expiry).
5. **`GET /metrics` exists in v1**, ahead of PRD §11's full observability spec. Prometheus text format, three counters (`zerocache_cache_hits_total`, `zerocache_cache_misses_total`, `zerocache_provider_prompt_tokens_total`) — deliberately scoped to just what Phase 1's success criteria (§15: measured hit rate, measured tokens billed) need, not per-consumer tagging or latency-saved-vs-baseline, which need decisions not yet made. Chosen over a bespoke JSON endpoint specifically because with `zerocache-adapters-redis` multi-replica deployments, per-pod counters only mean something once something aggregates across pods — Prometheus's scrape-and-`sum()` model does that; a single pod's JSON response can't.
6. **v1's single operator-configured provider (`ZEROCACHE_PROVIDER_API_KEY`) is gone, replaced by per-request bring-your-own-key (2026-07-24).** PRD §6.4/§4 describe additional provider adapters as "Future" work behind one operator-configured provider — this goes further: any of four providers (`openai`, `mistral`, `gemini`, `huggingface` — the last added later, item 15 below) can be selected per-request via the URL path, using the caller's own forwarded key, never Zerocache's. This also activates PRD §7's previously-deferred namespacing: `CacheKey` now includes an `owner_id` (a hash of the caller's key, never the raw key) alongside `provider`, `model`, `model_version`, `text`. Full reasoning in `decisions.md`.
7. **`EmbeddingProvider` is async (2026-07-24).** Adapters use async `reqwest`, removing the earlier `reqwest::blocking`-inside-`spawn_blocking` overhead (two runtimes, a thread-pool hop per request) — this was a real architectural wart, not a style choice; see the note in memory/commit history about why `main()` originally couldn't be `#[tokio::main]`. It can be again now. Each adapter also chunks input into batches of `MAX_BATCH_SIZE = 100` (a single conservative constant, not a verified per-provider limit — see `decisions.md`), and `version()` replaces the old global `model_version` string, tying cache-key versioning to each adapter crate's own `Cargo.toml` version instead of a manually-bumped convention.
8. **Production-trust Tier 1 (2026-07-24): provider timeouts, graceful shutdown, `/health`+`/ready`, store-call timeouts.** All three provider adapters now build their `reqwest::Client` with a uniform, unmeasured `PROVIDER_TIMEOUT = 30s` (same rationale as `MAX_BATCH_SIZE`: no verified per-provider SLA exists to tune to) — previously `reqwest::Client::new()` had no timeout at all, so a hung upstream connection blocked a request forever. `zerocache-http`'s server now shuts down gracefully via `axum::serve(...).with_graceful_shutdown(shutdown_signal())`, resolving on Ctrl+C (all platforms) or, `#[cfg(unix)]` only, `SIGTERM` (what Kubernetes sends before force-killing a pod) — **verified for real, not just read for correctness: built and ran natively on Linux via WSL2 Ubuntu, sent a genuine `kill -TERM`, confirmed the shutdown log line, a clean `exit code 0`, and no dropped in-flight request.** New unauthenticated `GET /health` (zero I/O, proves only that the process/router is up) and `GET /ready` (calls `check_store_readiness`, which reuses the existing `EmbeddingStore::get` — no new port-trait method — against a fixed reserved sentinel key that's never written to; a miss is healthy, only a store-level error means not-ready) join `/metrics` as infrastructure-facing endpoints outside the versioned API contract. Store calls (`sled`/`redis` `get`/`put`/`delete`, run via `spawn_blocking`) are now also bounded: `zerocache-http/src/app.rs`'s `run_store_task` wraps every store call in a 5s `tokio::time::timeout` uniformly (any backend degrades into a fast `AppError::Store` instead of an indefinite hang — this is what makes `/ready` fail fast instead of hanging right along with a wedged store, and keeps a stuck store call from stalling the graceful-shutdown drain); `zerocache-adapters-redis` additionally sets real socket-level `set_read_timeout`/`set_write_timeout` (5s) on every checked-out connection, which is the layer that actually unblocks a stale TCP connection at the OS level rather than just bounding how long the caller waits for it.
9. **`input` accepts a bare string, not just an array (2026-07-24) — found via real LangChain TS battle-testing, not a synthetic edge case.** `EmbeddingsRequest.input` in `zerocache-http/src/wire.rs` previously required a JSON array (`Vec<String>`), rejecting a bare JSON string with `422`. OpenAI's real `/v1/embeddings` contract accepts `input` as either shape, and `@langchain/openai`'s `embedQuery()` — a first-class, extremely common method, not an edge case — sends the bare-string form for any single-text embed. This also broke `MemoryVectorStore.similaritySearch()`'s query-embedding step under the hood, meaning a real RAG app's actual question-answering path failed 100% of the time against Zerocache, even though document ingestion (which always calls `embedDocuments()`, the array form) worked fine — a demo that looked like it worked until someone actually asked it a question. Fixed with a custom `deserialize_with` on `EmbeddingsRequest.input` (an untagged `String | Vec<String>` enum, single string wrapped to a one-element `Vec`); `DeleteRequest` shares the same struct so gets the fix for free. This is exactly the class of gap "battle-test against a real second consumer" exists to catch — CI/mocks alone would never have exercised this, since every test in the codebase up to this point constructed `input` as an array by convention, matching the plan/brief code rather than a real, unmodified client's actual wire behavior.
10. **Body-rejection errors now use the app's own error shape (2026-07-24).** Malformed JSON and valid-JSON-wrong-shape both used to return axum's default plain-text `JsonRejection` body, not `{"error": "..."}` like every other error path — a real inconsistency the LangChain TS battle-test flagged. Both `embeddings_handler` and `delete_handler` now take `Result<Json<EmbeddingsRequest>, JsonRejection>` instead of a bare `Json<EmbeddingsRequest>`, and map a rejection through a small `json_rejection_to_error_response` helper using `JsonRejection::status()`/`.body_text()` (generated by axum-core's `composite_rejection!` macro for every variant) — same status code and message axum already computed, just wrapped in the app's own envelope. Request-body validation still runs before the auth check, unchanged from before (extractors run in parameter order; `Json`/`Result<Json<_>, _>` is still the last parameter, so this doesn't change *when* the failure is detected, only *how* it's reported).
11. **In-process request coalescing (2026-07-24).** Concurrent requests that miss on the *exact same* `CacheKey` now share one provider call instead of each independently paying for it — the gap the LangChain TS battle-test measured directly: 5 concurrent misses on one never-before-seen text produced 5 real provider calls before this fix. `AppState.in_flight: Mutex<HashMap<CacheKey, Shared<...>>>` (a `futures::future::Shared`-wrapped boxed future per in-flight key) tracks fetches currently underway; `zerocache-http/src/app.rs`'s new `fetch_coalesced` checks it before calling the provider — a request either claims a key (nobody else fetching it, so it registers a shared future and does the real provider call) or piggybacks (clones an existing entry and awaits the same result). Only the claiming request's stats reflect real provider usage; a piggybacking request reports zero tokens for coalesced keys, the same as a cache hit, since no extra billing happened on its behalf. Deliberately scoped to **the store write itself staying un-deduped** (every resolver, claimer or piggybacker, still writes its own copy back) — redundant writes of an identical value are already this codebase's accepted correctness model (see the Redis adapter's own last-write-wins rationale), so coalescing the write too wasn't worth the added complexity. Also deliberately **in-process only**: two different replicas behind a load balancer each keep their own independent `in_flight` map, so the same miss can still be fetched once per replica — cross-replica coalescing would need a distributed coordination mechanism (e.g. a Redis-backed lock) and is real, separate, harder work, not built here. **(Cross-replica single-flight for the single-key case landed 2026-08-30 — see Deviations item 26. Multi-item batches remain in-process only.)** `ProviderError` gained `Clone` (zerocache-ports) so it can flow through a `Shared` future's cloned `Result`; `EmbedRequest.provider` changed from `&'a dyn EmbeddingProvider` to `Arc<dyn EmbeddingProvider>` so a coalesced fetch can build a `'static` future outliving any one request's stack frame. Proven with a dedicated test using a slow (artificially delayed) mock provider and 5 genuinely-overlapping concurrent `embed_batch` calls — asserts exactly 1 provider call and usage attributed exactly once, not per-request.
12. **Provider retry/backoff (2026-07-24).** All three provider adapters (`zerocache-adapters-openai`/`-mistral`/`-gemini`) now build their HTTP client as a `reqwest_middleware::ClientWithMiddleware` wrapping `reqwest::Client` with `reqwest_retry::RetryTransientMiddleware` (`ExponentialBackoff`, `MAX_RETRIES = 3`, a single conservative constant like `MAX_BATCH_SIZE`/`PROVIDER_TIMEOUT`, not tuned per-provider). Uses `reqwest-retry`'s `DefaultRetryableStrategy` as-is — retries 5xx/408/429/connection errors, never other 4xx — which is exactly the desired semantics with no custom configuration. Motivated by a real 429 hit against Gemini during the Python/LlamaIndex battle-test, not a hypothetical. Pinned to `reqwest-retry 0.7`/`reqwest-middleware 0.4` (with `features = ["json"]`, off by default) specifically because their latest majors (0.9/0.5) pull `reqwest 0.13`, conflicting with the `reqwest 0.12` already pinned workspace-wide.
13. **OpenTelemetry tracing (2026-07-24).** `zerocache-http/src/otel.rs`'s `otel::init()` installs a `tracing_subscriber` pipeline: a console `fmt` layer always on, plus an OTLP (gRPC/tonic) export layer only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set — no collector required to run Zerocache locally, matching the existing pattern for other optional env-gated behavior (`ZEROCACHE_TTL_SECONDS`). Uses `opentelemetry-otlp` with `--no-default-features --features grpc-tonic,trace` for the same `reqwest 0.13` vs `0.12` conflict reason as item 12 — the HTTP exporter's default features pull `reqwest-blocking-client`; gRPC/tonic has no `reqwest` dependency at all. An `EnvFilter` (`tracing-subscriber`'s `env-filter` feature) defaults to `info` and respects `RUST_LOG` — without it the default is "enable everything," which floods the console with `sled`'s internal TRACE-level logging (found via a real local smoke test, not assumed). `tower_http::trace::TraceLayer` gives every HTTP request its own span; `#[tracing::instrument]` on `embeddings_handler`/`delete_handler`/`embed_batch`/`delete_batch`/`fetch_coalesced` nests `store_lookup`/`provider_call`/`store_write_back`/`store_delete` child spans underneath, so a trace shows the full `HTTP handler → cache lookup → provider call → store write` path, with `hits`/`misses`/`claimed`/`piggybacked` recorded as span fields. `SdkTracerProvider::shutdown()` runs after `axum::serve(...)` returns, flushing the batch span exporter before process exit (skipped when OTLP isn't enabled, since there's nothing to flush).
14. **Multimodal image embeddings (2026-07-24): a separate `ImageEmbeddingProvider` port, implemented by Gemini only.** `zerocache-ports::ImageEmbeddingProvider` (`embed_image_batch(api_key, model, images: &[ImageInput]) -> Result<(Vec<Vec<f32>>, ProviderUsage), ProviderError>` plus `version()`) is a standalone trait, not an extension of `EmbeddingProvider` — verified live against `developers.openai.com/api/docs/guides/embeddings` at this feature's planning time (2026-07-24, before any of this feature's code was written, not re-checked at each implementation step) that OpenAI's public API surface has no image-embedding endpoint at all (its `/v1/embeddings` lists only text-only models), so a default-returns-"unsupported" method bolted onto `EmbeddingProvider` itself would force every current and future text-only adapter (`openai`, `mistral`, `huggingface`) to carry dead code for a capability none of them can ever have. `zerocache-adapters-gemini` is the only implementor, via `gemini-embedding-2` — Public Preview status as of 2026-07-24, same planning-time live check against `ai.google.dev/gemini-api/docs/embeddings` — reusing the same `:batchEmbedContents` endpoint and `x-goog-api-key` auth the existing text adapter already calls, just with an `inline_data` content part instead of a text part. Each image gets its own independent embedding (one `content` entry per image in the batch request), deliberately not using Gemini's separate interleaved-multimodal capability that combines up to 6 images into one shared vector — a different feature with different cache-key semantics, not built here. `zerocache_core::CacheKey::derive_image` is domain-separated from the existing text `derive` via an `"image\0"` literal folded into the hash below the model-version field: this guarantees an image-derived key can never collide with a text-derived key even if an image's base64 payload happens to equal some unrelated cache entry's literal text byte-for-byte — a real, not hypothetical, edge case once both content types share one `EmbeddingStore`. New routes `POST`/`DELETE /{provider}/v1/images/embeddings` (see API contract below) reuse the existing `EmbeddingsRequest` wire struct rather than a new one (`DeleteRequest`/`DeleteImageRequest` are `zerocache-http/src/app.rs`-internal structs built from the already-parsed `EmbeddingsRequest`, not JSON-deserialized wire types themselves) — a caller sends one or more `data:<mime>;base64,<data>` strings as `input` instead of literal text, parsed by `zerocache-http/src/image.rs`'s `parse_data_uri`. Image embedding is deliberately simpler than the text path in one way, not an oversight: no text normalization (images aren't normalized). It does dedupe within-batch since 2026-07-27 — see item 16. **(Superseded 2026-08-07 by item 20: cross-request coalescing, originally deferred here as "a second, image-specific in-flight map is real, separate work, not built here," is now built.)** All three Prometheus counters (`zerocache_cache_hits_total`/`_misses_total`/`_provider_prompt_tokens_total`) gained a `content_type` label (`"text"` or `"image"`) alongside the existing `provider` label, so the two paths' hit rates are distinguishable in `/metrics`, not conflated.
15. **`zerocache-adapters-huggingface`: a fourth text-embedding provider, `EmbeddingProvider` only (2026-07-24).** HuggingFace's Inference Providers API also has no image/CLIP-embedding endpoint — same planning-time live check (2026-07-24, before this feature's code was written) against `huggingface_hub`'s own source (`github.com/huggingface/huggingface_hub`) and the current Inference Providers docs (`huggingface.co/docs/inference-providers`) — so, like `openai` and `mistral`, it implements `EmbeddingProvider` and nothing else; `AppState.image_providers` is never populated with a `huggingface` entry, so `POST`/`DELETE /huggingface/v1/images/embeddings` `404`s for the same structural reason `/openai/...` and `/mistral/...` do (item 14 above) — no extra enforcement code, it falls out of a missing map key. The one real architectural difference from the other three adapters: the model is part of the URL path (`{base_url}/models/{model}/pipeline/feature-extraction`), not a JSON body field, because HuggingFace's unified, body-based router (`router.huggingface.co/v1/...`) is documented as chat-completions-only and explicitly excludes embeddings — a genuinely different wire shape, not a stylistic choice, and it still fits the existing `EmbeddingProvider` trait unchanged since `model: &str` was already a per-call parameter (item 1 above), just built into the URL inside `embed_batch` instead of the request body. The response is also shaped differently: a bare `Vec<Vec<f32>>` with no wrapping object and no usage/token field at all (confirmed absent from HuggingFace's own API spec) — never reported, same posture as Gemini. Otherwise follows the same pattern as the other three adapters exactly: `MAX_BATCH_SIZE = 100` chunking, `PROVIDER_TIMEOUT = 30s`, and the `reqwest-retry`/`reqwest-middleware` retry-on-transient-5xx/429 wrapper (items 7, 8, 12 above).

16. **Within-batch image dedup (2026-07-27).** `embed_image_batch` (`zerocache-http/src/app.rs`) now dedupes misses that share a `CacheKey` within one batch — two images with identical bytes + mime type are embedded and stored once, with the same vector broadcast back to every matching position, instead of paying the provider once per occurrence. Same bookkeeping shape `embed_batch` already uses for text (a `key_to_unique_index: HashMap<CacheKey, usize>` mapping original indices to a deduplicated call list), applied without the corresponding text-only normalization/coalescing steps. Closes the gap item 14 originally called out as deliberately deferred — proven with `duplicate_images_in_one_batch_call_provider_only_once`, mirroring `duplicate_texts_in_one_batch_call_provider_only_once`.
17. **Configurable provider base URLs (2026-07-27).** Four new optional env vars — `ZEROCACHE_OPENAI_BASE_URL`, `ZEROCACHE_MISTRAL_BASE_URL`, `ZEROCACHE_GEMINI_BASE_URL`, `ZEROCACHE_HUGGINGFACE_BASE_URL` — override the base URL each adapter is constructed with in `zerocache-http/src/main.rs`, defaulting to today's hardcoded real-provider endpoint when unset (`https://api.openai.com`, `https://api.mistral.ai`, `https://generativelanguage.googleapis.com`, `https://router.huggingface.co/hf-inference` respectively). The adapters themselves already accepted an arbitrary `base_url` constructor argument — that's how their own test suites point them at a mock `httpmock` server — so this is purely a `main.rs`/`Config` wiring change, not new adapter code. Scope is deliberately narrow: this only helps for endpoints that speak the *exact same wire protocol* as the real provider (self-hosted vLLM/LM Studio/TGI serving OpenAI's `/v1/embeddings` shape, an on-prem Mistral-compatible proxy, a self-hosted HuggingFace TEI instance) — it does **not** add support for Azure OpenAI, Amazon Bedrock, or GCP Vertex AI, none of which are a base-URL swap (different auth schemes, different wire shapes, and in Bedrock/Vertex AI's case, multiple embedding vendors behind one API). Those are separate, deliberately-deferred future work — see `docs/superpowers/specs/2026-07-27-configurable-provider-base-urls-design.md`'s "Relationship to future work" section. Each override's expected value is a bare origin (scheme + host + optional port) with no `/v1` suffix and no trailing slash — every adapter builds its request URL as `format!("{}/v1/embeddings", self.base_url)` (or similar per-adapter path), so a value copied from a tool that prints its own base URL already including `/v1` (a common convention this inverts) produces a confusing double-`/v1` 404 rather than a clean failure. **(Superseded 2026-07-28 by item 18, which adds all three as real adapters.)** The scope boundary described here was accurate for Phase A; item 17's env vars remain exactly what they were, for wire-shape-compatible self-hosting only.

18. **A generalized cloud adapter layer: Azure, Amazon Bedrock, and GCP Vertex AI (2026-07-28).** Deviations item 17 said the base-URL work "does **not** add support for Azure OpenAI, Amazon Bedrock, or GCP Vertex AI" and deferred them; this is that deferred work. Each of those three clouds is one API in front of *several independent vendors* with different request/response JSON, so they are not three more copies of the existing adapter pattern — they share a new kit crate, `zerocache-adapters-cloud`, holding the HTTP transport driver (client construction, `PROVIDER_TIMEOUT`/`MAX_RETRIES`, chunking, count checking, usage accumulation) and a two-level strategy abstraction: `CloudRouter` (one per cloud — parses the caller's `model` string into concrete coordinates and picks a strategy) and `TextWireStrategy` (one per vendor shape — builds the request bytes, parses the response, and declares its own `max_batch()`). `CloudProvider<R: CloudRouter>` is the only `EmbeddingProvider` implementation among them. The kit sits between `zerocache-ports` and the three cloud crates, so dependencies still point inward only and no adapter depends on another adapter; the four existing adapters were deliberately **not** migrated onto it (a large diff with no user-visible benefit, and it would have dragged four working adapters into this change's blast radius). Multi-vendor selection happens entirely through the caller's `model` string — no new wire field, since `model` is already free-form per-request, already lands in the cache key, and is settable from any framework, whereas a custom body field would break the "no framework-specific SDK" non-goal. The grammars: `bedrock` takes `[<region>/]<modelId>[#<input_type>]` and dispatches on vendor prefix (`amazon.titan-embed*` → a scalar-`inputText` strategy with `max_batch = 1`, since Titan's field is a string not an array; `cohere.embed*` → a `texts`-array strategy with `max_batch = 96`), authenticating with the caller's Bedrock API key as `Authorization: Bearer` — no AWS SigV4 anywhere, which is possible because AWS ships first-class bearer API keys for `bedrock-runtime`. `vertexai` takes `[<location>/<project>/]<modelId>[#<task_type>]` against the native `:predict` endpoint (Vertex's OpenAI-compatible surface is chat-completions only, verified — it cannot reuse the OpenAI adapter), with one strategy shared by all three supported models — `text-embedding-005`, `text-multilingual-embedding-002`, and `gemini-embedding-001` all carry the same `max_batch = 250`, Google's current documented limit applying uniformly with no per-model carve-out. It is the first new adapter since Mistral to report real usage, summed from `predictions[].embeddings.statistics.token_count`. A live-docs re-verification pass on 2026-07-29/30 found that this max_batch figure (originally recorded at plan-writing time as 250 for the first two models but exactly 1 for `gemini-embedding-001`) and a related endpoint-host defect (`global`/`us`/`eu` locations resolving to the wrong host) had both gone stale/wrong since planning, and fixed both in commit `0220074` — a concrete instance of why "mock-only, no live-key smoke test" (noted below for all three clouds) makes periodic doc-vs-code re-verification necessary, not just a one-time planning-time check. `azure` takes `[foundry:]<deployment>[#<input_type>]` across Azure's *two* embedding surfaces — the GA `/openai/v1/embeddings` path (OpenAI models only, no `api-version` query parameter) and Foundry Models' `/models/embeddings?api-version=…` on a different hostname, which is where the non-OpenAI vendors like Cohere live — with `ZEROCACHE_AZURE_AUTH_MODE` selecting `Authorization: Bearer <entra token>` (default, Microsoft's recommendation) or `api-key: <key>`. The `#` qualifier on Bedrock/Vertex/Foundry carries `input_type`/`task_type`, which are required-or-near-required parameters that *change the output vector*; hardcoding one would silently give every caller document-style embeddings even for queries, and the failure mode would be invisible (vectors look fine, retrieval degrades), so it is caller-controlled and part of the cache identity. Nine new optional env vars configure defaults (`ZEROCACHE_AZURE_OPENAI_BASE_URL`, `_AZURE_FOUNDRY_BASE_URL`, `_AZURE_FOUNDRY_API_VERSION`, `_AZURE_AUTH_MODE`, `_BEDROCK_REGION`, `_BEDROCK_ENDPOINT_TEMPLATE`, `_VERTEX_PROJECT`, `_VERTEX_LOCATION`, `_VERTEX_ENDPOINT_TEMPLATE`); `bedrock` and `vertexai` register unconditionally, `azure` only when its base URL is set, since an Azure resource name *is* its hostname and there is no default — with it unset, `/azure/v1/embeddings` 404s out of a missing map key, no enforcement code needed, the same way `/openai/v1/images/embeddings` already does. Image embeddings on these clouds are deliberately deferred (Cohere Embed v4 and Vertex `multimodalembedding@001` both support them; `ImageEmbeddingProvider` is a separate trait precisely so that lands independently later). All wire shapes were verified live against each vendor's own current documentation on 2026-07-28, at this feature's planning time, before any code was written — `learn.microsoft.com/en-us/azure/foundry/openai/how-to/embeddings`, `docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_InvokeModel.html` plus the per-model parameter pages, and `docs.cloud.google.com/vertex-ai/generative-ai/docs/embeddings/get-text-embeddings`. **All three ship mock-only: none has had a live-key smoke test**, the same caveat `zerocache-adapters-huggingface` already carries. One known open risk, recorded rather than solved: `owner_id` is a hash of the caller's credential, and a GCP OAuth2 access token lives about an hour, so a Vertex caller's cache namespace rotates with their token — usable for a single long ingestion run, but not across days. Full design and the two candidate fixes in `docs/superpowers/specs/2026-07-28-cloud-provider-adapter-layer-design.md`.
19. **`CacheKey` gained a `cache_scope` component (2026-07-28) — a breaking change that invalidated every existing cache entry, once.** `zerocache-http/src/main.rs`'s `warn_on_overridden_base_urls` used to carry a doc comment admitting a real hole: `CacheKey::derive` hashed `owner_id + provider + model + model_version + text`, where `provider` was just the URL path segment, so repointing `ZEROCACHE_OPENAI_BASE_URL` at a self-hosted vLLM silently reused vectors computed by `api.openai.com`. That was a startup-time footgun with one env var; item 18's cloud adapters would have made it a *per-request* correctness bug, since `amazon.titan-embed-text-v2:0` in `us-east-1` and in `eu-west-1`, or `text-embedding-005` under two different GCP projects, are the same `model` string against genuinely different upstreams. Both `CacheKey::derive` and `CacheKey::derive_image` now take a `cache_scope: &str` immediately after `provider`, sourced from a new required method on **both** port traits, `fn cache_scope(&self, model: &str) -> Result<String, ProviderError>`. It is required rather than defaulted because every adapter has a real answer — the four wire-shape-fixed ones return their configured `base_url`, and `CloudProvider` returns `{endpoint_base}\0{canonical}\0kit{version}` (`\0`-joined, mirroring `zerocache-adapters-cloud/src/driver.rs`'s `cache_scope`), folding in the kit's own version so a shared-driver behavior change invalidates cloud entries that no cloud crate's version bump would have caught. (The opposite reasoning to item 14's, where a defaulted `ImageEmbeddingProvider` method was rejected precisely *because* it would have been dead code for every text-only adapter.) `zerocache-http/src/app.rs` resolves it once per batch, next to the existing `provider.version()` call, never once per text. The cost, stated plainly because it is real: every cache entry written before this change became unreachable. Not corrupt — content-addressed entries are never wrong, only absent, and CLAUDE.md already treats eviction as a capacity concern rather than a correctness one — but a one-time cold start for every deployment. That was judged the correct price, because the alternative is a cache that can serve a `us-east-1` vector to a `eu-west-1` request, and a wrong vector is silent in a way a cold start never is. `warn_on_overridden_base_urls` was accordingly rewritten as `log_overridden_base_urls`, downgraded from `warn` to `info`, and now says the opposite thing: repointing produces a cold cache, not stale hits.

20. **Image-embedding request coalescing (2026-08-07) — the image counterpart to item 11, closing the gap item 14 originally deferred.** Concurrent requests missing on the *exact same* image `CacheKey` now share one provider call instead of each paying for it independently, exactly like the text path already did. `AppState.image_in_flight: Mutex<HashMap<CacheKey, Shared<...>>>` is a second, separate in-flight map alongside the existing text-only `in_flight` — not a shared one, deliberately: an image key and a text key can never collide (`CacheKey::derive_image` is already domain-separated from `derive`, item 14), but keeping the maps apart also means a burst of image traffic can never contend the text path's lock, and vice versa. `zerocache-http/src/app.rs`'s new `fetch_image_coalesced` mirrors `fetch_coalesced` exactly — claim vs. piggyback under a short-held `std::sync::Mutex` never held across an `.await`, `futures::future::Shared` so every waiter gets its own cloned `Result` — and reuses the *same* `SharedFetch`/`SharedFetchOutput` type aliases `fetch_coalesced` already used, since they were generic over `CacheKey -> Vec<f32>` + `ProviderUsage`/`ProviderError` with nothing text-specific baked in; no new type aliases were needed. `embed_image_batch` now calls `fetch_image_coalesced` instead of calling `ImageEmbeddingProvider::embed_image_batch` directly on every miss. `ImageInput` (zerocache-ports) gained `#[derive(Clone)]` so a coalesced fetch can cheaply clone an image into the `'static` future backing the shared in-flight entry, the same way `String` texts are already cloned for the text path. Deliberately unchanged: within-batch dedup (item 16) still runs first, so `fetch_image_coalesced` only ever sees the unique misses within one caller's own batch — coalescing operates *across* concurrent requests, not *within* one. Cross-replica coalescing (item 26) does **not** cover images — `fetch_image_coalesced` stays in-process only. Proven with `concurrent_identical_image_misses_across_separate_requests_are_coalesced_into_one_provider_call`, mirroring the text path's `concurrent_identical_misses_across_separate_requests_are_coalesced_into_one_provider_call` test: 5 concurrent requests missing on one never-before-seen image assert exactly 1 real provider call and usage attributed exactly once, not per-request.

21. **Semantic LLM completion cache — v1 (2026-08-28).** A new surface, `POST /{provider}/v1/chat/completions`, that caches whole chat completions, not embeddings — the first thing in the repo that isn't an embedding cache. Money model (agreed before building): a single monotonic agent run gets ~zero completion-cache hits (every turn's prompt is strictly longer than the last); the savings come from **repeated runs** (CI/eval loops, prompt tuning, re-asks — a full hit is 100% off input *and* output, versus provider-side prompt caching's input-only discount on a request that still runs), **auxiliary agent LLM calls** (short "summarize this" / "classify that" calls that recur across runs), **retry/flap storms**, and **multi-agent fan-out** with templated prompts. New pieces: `zerocache_core::canonicalize_completion_request` (order-independent serialization of the output-affecting request fields — a **denylist** of non-output-affecting keys: `model`/`user`/`stream`/`stream_options`/`store`/`metadata`, so an unrecognized param stays in the key, an unnecessary miss over a wrong completion) and `completion_request_is_cacheable` (determinism gate: `temperature == 0` **or** an explicit `seed`, `n` absent/1, non-empty `messages`; ignores `stream`); `CacheKey::derive_completion`, domain-separated from `derive`/`derive_image` via a `"chat-completion\0"` literal; ports `CompletionStore` (opaque `Vec<u8>` get/put/delete) and `ChatCompletionProvider` (`chat_completion(api_key, &serde_json::Value) -> ChatCompletionResponse` — a non-2xx upstream response is `Ok` with the real status, `Err` is transport-only, so the proxy forwards error bodies verbatim and never caches them); `CompletionStore` impls on both `SledStore` (dedicated `"completions"` tree, same 8-byte LE expiry prefix so `ZEROCACHE_TTL_SECONDS` applies) and `RedisStore` (`"zerocache:completion:"` key prefix, native `SET EX`) — both structs now implement two store traits, so their own tests disambiguate the shared `get`/`put`/`delete` names, callers going through `Arc<dyn _>` don't; `ChatCompletionProvider` on `OpenAiProvider` (thin proxy to `{base_url}/v1/chat/completions`, reuses the existing retry/timeout client); `zerocache-http/src/completion.rs` (`complete()` orchestration + `fetch_completion_coalesced`, the single-key completion counterpart to `app.rs`'s batch `fetch_coalesced`, against a new `AppState.completion_in_flight` map). The stored record is `{body, prompt_tokens, completion_tokens, total_tokens}` so a hit knows exactly what the caller was *not* billed — surfaced as four new provider-labeled `Metrics` counters, `zerocache_completion_cache_hits_total` / `_misses_total` / `_prompt_tokens_saved_total` / `_completion_tokens_saved_total` (note "saved", not "billed" — the completion path measures avoided cost, the embedding path measures spent cost). Response carries `X-Zerocache-Completion-Hit: true|false`. A stored record that no longer deserializes is treated as a miss, not an error (same "content-addressed entries are absent, never wrong" posture as everywhere else). **Deliberately deferred** (each is real, separate work): the local-ONNX-embedder semantic-similarity tier (the "near-identical *intent*" match, gated by a conservative cosine threshold — the threshold, not embedder quality, is what controls false-positive wrong answers; small `bge-small`/`MiniLM`-class model chosen so it works for every chat provider including Claude, adds no second key, adds no per-request latency, and can't rot); Anthropic `/v1/messages` wire shape; a `DELETE /{provider}/v1/chat/completions`; registering `mistral`/cloud adapters as chat providers. **(Single-key cross-replica coalescing for completions landed 2026-08-30, Deviations item 26.)** **(Streaming `stream:true` buffer-and-replay landed 2026-08-30, Deviations item 27.)** Tests: `zerocache-core` +20 (`completion` module), `zerocache-http` +8 (`completion` module — passthrough-when-ineligible, miss→store→hit, non-2xx not cached, per-owner scoping, key-irrelevant-field still hits, generation-param change misses, tokens-saved metric, concurrent-miss coalescing), `zerocache-adapters-openai` +6, `zerocache-adapters-sled` +6, `zerocache-adapters-redis` +4 (`#[ignore]`d, Docker — not run in the authoring environment). **Live smoke test (2026-08-28):** run against a real instance with `ZEROCACHE_OPENAI_BASE_URL` pointed at Gemini's OpenAI-compatible endpoint (`https://generativelanguage.googleapis.com/v1beta/openai`), model `gemini-3.5-flash-lite`, a real key. Both `demo/completion-cache/battle-test.mjs` (a dependency-free scripted 4-turn loop + one auxiliary prompt ×8, diffing the `zerocache_completion_*` counters) and the new `demo/completion-cache/agent.mjs` (a real ReAct tool-calling agent — `search_kb`/`get_order`/`resolve_ticket` over in-script data — resolving a 3-ticket suite twice) pass: the repeat run is 100% cache hits with zero upstream calls, **every intermediate tool-call turn included**, and byte-identical resolutions. 23. **Live savings dashboard at `GET /dashboard` (2026-08-29).** A single-page app that visualizes what a running instance has saved — hit rates, tokens not billed, an estimated dollar figure, a per-provider table, and a session chart of cost avoided over time — by polling `/metrics` every 2s from the browser. Built with **Astro + React islands + Recharts** (the user asked for a real framework and charting lib, not hand-rolled HTML), living in a new top-level `dashboard/` directory that is its own npm project. So `cargo build` needs no Node — only *rebuilding the dashboard* does. Served same-origin as `/metrics`, so no CORS. New dep: `include_dir` (compile-time asset embed, no transitive deps). Savings math: completions are exact (the stored response's `usage` block says what a hit was not billed → `tokens_saved/1e6 × price`); embeddings are estimated (`hits × avg tokens per observed miss`, or `× an assumed size` set in the UI when no miss has been seen), since the embedding metrics only expose tokens *billed*, not a per-hit count. Prices are illustrative defaults, editable in-page and persisted to `localStorage`; recompute is instant, no poll wait. Counter resets on process restart are detected (a backwards jump) and clear the session chart. Colors follow the dataviz reference palette (single blue series + status green); light/dark/system theme toggle. `zerocache-http` +3 tests in a `dashboard` module — the embed contains `index.html`, the built JS bundle still references every `/metrics` family name the Rust side emits (fails loudly on a counter rename instead of the dashboard silently showing zeros), and content-type mapping. **Deliberately not done:** auth on `/dashboard` (matches `/metrics`), historical/persisted metrics (the chart is per-page-load only), embedding-token exactness (would need a new counter). The committed `dist/` is a Node-less-build convenience; the Docker image (2026-08-29) rebuilds it in a `node:22` stage rather than trusting the checked-in bytes, and CI only type-checks/builds it (no byte-diff — bundler output is not cross-platform reproducible). **Live-verified 2026-08-29** against a real instance with Gemini traffic: HTML + assets serve, polling/reset-detection/price-edit-recompute/theme-toggle/chart↔table all work; a mid-session price edit rescaled the chart and stepped the cumulative line live. 24. **Semantic completion cache — opt-in (2026-08-29).** Roadmap item 1. Turns the near-zero exact-match hit rate on paraphrased chat traffic into a useful one: on an exact-match *miss* for a cacheable (deterministic) `POST /{provider}/v1/chat/completions`, embed the configured "fuzzy" span of the request with a local model and accept a previously-served completion if a) a blake3 hash of the *rest* of the request matches byte-for-byte **and** b) cosine similarity ≥ a conservative threshold. The threshold, not the embedder, bounds false positives. **Compile-time gated behind `--features semantic`** — the default build and image are byte-identical to before (still `FROM scratch` + musl, still ~14.7 MB; the `build-musl` job and default `docker build` confirmed unchanged). The tier lives in a new **non-workspace-member** crate `zerocache-semantic` (candle + `all-MiniLM-L6-v2` f16 safetensors, ~45 MB, `include_bytes!`d in; `hnsw_rs`; `tokenizers` with the pure-Rust `fancy-regex` backend, no `onig` C dep), so `cargo build --workspace` / `cargo test --workspace` never compile candle — build/test it with `--manifest-path zerocache-semantic/Cargo.toml` or `-p zerocache-http --features semantic`. **Runtime opt-in even in a semantic build:** off unless `ZEROCACHE_SEMANTIC=1`; `ZEROCACHE_SEMANTIC_THRESHOLD` (default `0.97`, clamped to `[0.5, 1.0]` or reset to default); `ZEROCACHE_SEMANTIC_MATCH_UNIT` = `last-user` (default — embed only the final user message; everything else exact) \| `system-and-last-user` \| `full-conversation`. 25. **Multi-replica semantic completion index — Redis Stream change-feed (2026-08-29).** Roadmap item 1's redis half. Item 24 shipped the semantic tier sled-only; `ZEROCACHE_SEMANTIC=1` on the redis backend used to log a `warn` and fall back to exact-match. It now works across N replicas. **New port method** `CompletionVectorStore::changes_since(cursor: Option<String>) -> Result<VectorChanges, StoreError>` (`VectorChanges { upserts, deletes: Vec<(CacheKey, [u8;32])>, cursor: Option<String> }`); `CompletionVectorStore::delete` gained a `scope_hash: &[u8;32]` param (the sole caller, `semantic_probe`'s self-heal, already had it) so a remote tombstone lands on the right per-scope graph in O(1). **sled** returns `VectorChanges::default()` (`cursor: None`) and keeps its `load_all` boot path. **redis** implements `CompletionVectorStore` (new `zerocache-adapters-redis/src/vector.rs`) over **one global stream `zerocache:semantic:events`**: `insert` → `XADD op=put k=<hex> s=<hex> c=<hex> iv=<n> v=<base64 f32le>` with `MAXLEN ~ ZEROCACHE_SEMANTIC_INDEX_MAXLEN` (default 100 000) on every write, plus an opportunistic `XTRIM MINID ~ <now_ms − ttl_ms>` when `ZEROCACHE_TTL_SECONDS` is set; `delete` → `XADD op=del k s`; `load_all`/`changes_since` → paged `XRANGE` (`COUNT 1000`) folded by `exact_key`, last op wins. **Requires Redis ≥ 6.2** for the exclusive `XRANGE (<id>` range and `XTRIM MINID` (`docker-compose.yml` already pins `redis:7`). Boot replay folds the whole stream into memory before inserting, so a replica's startup RSS peaks near 2× its resident index (~330 MB at the default cap) before settling. The adapter never filters on `index_version` (verbatim, like `SledStore::load_all`); `zerocache-http` skips `index_version != SEMANTIC_INDEX_VERSION` at replay. **Propagation is poll, not push:** `zerocache-http` boots the redis index from `changes_since(None)` (fold + cursor, no separate high-water query, no snapshot race) and runs **one `tokio` background task per process** that calls `changes_since(cursor)` every `ZEROCACHE_SEMANTIC_POLL_MS` (default 2000, clamped `[250, 60000]`) via `spawn_blocking` and applies remote upserts/deletes to the in-memory `SemanticIndex`. The query path is unchanged from item 24 — a local in-memory HNSW KNN, sub-ms, zero network. ~2 s propagation lag is benign: a not-yet-propagated vector is a semantic miss that falls through to the exact fetch ("absent, never wrong"). **(Superseded 2026-08-31 by Deviations item 29: the poll task now loops on a new `CompletionVectorStore::changes_blocking` — an `XREAD BLOCK` on the redis backend — so propagation lag drops from ~half the interval to one round-trip and an idle feed makes zero `XRANGE` calls. `ZEROCACHE_SEMANTIC_POLL_MS` keeps its name and `[250, 60000]` clamp but now bounds the `XREAD BLOCK` duration, i.e. how long a wedged read goes unnoticed and how long the post-error retry waits.)** `SemanticIndex::insert` is now idempotent per `exact_key` per scope (a `by_key` map; a re-delivered content-addressed vector clears any tombstone instead of adding a duplicate node); `tombstone` is O(1). **Failure posture:** Redis down at boot → `warn`, empty index, poll task still spawned with a `"0-0"` cursor and self-heals (**no `exit(1)`** — that stays reserved for embedder-load failure); Redis down mid-run → keep cursor, rate-limited `warn`, retry; malformed/newer-format stream entry → skipped, cursor advances, `warn` once per call; cursor trimmed past → `XRANGE` resumes from the new start, missed `put` → later semantic miss, missed `del` → stale node self-healed by `semantic_probe` (both benign); a `put`-then-`del` where all but the `put` was trimmed can produce one bounded stale semantic hit before the self-heal re-tombstones (accepted, recorded). **Config:** `ZEROCACHE_SEMANTIC_INDEX_MAXLEN` (usize, default 100 000, `0`/unparseable → default + `warn`), `ZEROCACHE_SEMANTIC_POLL_MS` (u64, default 2000, clamp `[250, 60000]` + `warn`). No new opt-in flag — implied by `ZEROCACHE_SEMANTIC=1` + `ZEROCACHE_STORAGE_BACKEND=redis`. **New metric** `zerocache_semantic_index_events_applied_total{op}` (`op` ∈ `upsert`|`delete`), bumped by the poll task; dashboard guard test + `metrics.ts` updated. **Deliberately deferred** (each its own project): the RediSearch / `FT.SEARCH KNN` native path (needs the module, adds a per-probe round-trip); ~~push propagation (pub/sub or `XREAD BLOCK`) to cut the poll lag~~ (landed 2026-08-31, Deviations item 29 — `XREAD BLOCK`); stream compaction beyond `MAXLEN`/`MINID`; an index-size gauge; the image semantic tier; Anthropic/`DELETE` (still from item 24; streaming buffer-and-replay landed 2026-08-30, Deviations item 27). **Tests:** `zerocache-ports` +2, `zerocache-adapters-redis` +6 (`#[ignore]`d testcontainer), `zerocache-adapters-sled` +1, `zerocache-semantic` +2, `zerocache-http` +6 (config +2, semantic module +3, metrics +1). No live multi-replica test — mock-only, matching the redis-adapter posture everywhere in this codebase. Design: `docs/superpowers/specs/2026-08-29-multi-replica-semantic-index-design.md`. 26. **Cross-replica request coalescing — opt-in, single-key (2026-08-30).** Roadmap Project 2. The in-process coalescing of items 11 / 20 / 21 dedupes concurrent identical misses *within one process*; behind a load balancer, N replicas still each pay the provider once for the same miss. This adds a Redis-backed distributed single-flight for the **single-key** case: every chat completion, and every embedding request whose batch reduces to one unique missing key after in-process dedup. Multi-item embedding batches and image embeddings stay in-process only. New port `zerocache_ports::CoalescingCoordinator` (synchronous, like the store traits: `try_lead(&key) -> Role::{Leader,Follower}`, `complete(&key)`, `follow(&key, wait: Duration) -> FollowSignal::{Signalled,WaitElapsed}`), with `RedisCoordinator` (in `zerocache-adapters-redis`, new `coordinator.rs`: `SET NX PX 60000` lock keyed `zerocache:coalesce:lock:<32 raw CacheKey bytes>`, value a per-process replica id; release via a `GET`-guarded Lua `DEL` so it never deletes a successor's lock, then `PUBLISH zerocache:coalesce:done:<key>`; a background `std::thread` `psubscribe`s `zerocache:coalesce:done:*` and wakes a per-key `Condvar`) and `NoopCoordinator` (in `zerocache-http/src/coalesce.rs`, always `Leader`). `zerocache-adapters-redis` gains **no new dependency** — the coordinator is `std` threading + the `redis` crate's own sync pub/sub. `AppState.coordinator: Arc<dyn CoalescingCoordinator>` is always present, built in `main.rs` from `(storage_backend, cross_replica_coalescing)` — `RedisCoordinator` only on `(redis, true)` (hard boot failure if the connect fails), a startup `warn` + `NoopCoordinator` on `(sled, true)`, `NoopCoordinator` otherwise. `zerocache-http/src/coalesce.rs::coalesce_cross_replica` wraps the single-key provider call: leader → call + `complete`; follower → re-read the store every ~250 ms while listening for the pub/sub wake, up to a 30 s deadline (= `PROVIDER_TIMEOUT`), then one promotion attempt, then its own call (accepts the rare duplicate). Three ordering rules make that wait a poll rather than a spin, all fixed in review (2026-08-30): the leader writes its single key to the store **inside** the coalesced fetch, before `complete` publishes, so `done` implies a readable entry (the caller's own write-back stays, an identical content-addressed value, and is the write that surfaces a store error); the pub/sub wake is **edge-triggered** (a per-slot generation counter `follow` snapshots on entry — a level flag would make every later `follow` for that key return instantly and turn the loop into a full-rate poll); and a follower that sees `Signalled` with the entry **still absent** breaks straight to the promotion attempt, since that combination means the leader finished and stored nothing (a non-2xx or a transport error). Worst-case single-key latency with the flag on is additive, ~60 s (the full deadline, then this request's own call under the 30 s `PROVIDER_TIMEOUT`), where it was ~30 s — now reached only when a leader holds the lock and never signals at all. It runs *inside* the existing `futures::Shared` in-flight future, so in-process piggybackers transparently get a peer's fill too (a piggybacker is still counted as a miss, per item 21; only the request that actually waited cross-replica is counted as the coalesced hit). Design decisions (settled with the user): single-key only (a K-lock multi-key protocol is deferred); hybrid pub/sub + poll wait (poll alone was the fallback-only option); explicit `ZEROCACHE_CROSS_REPLICA_COALESCING` opt-in (truthy set `{"1","true","yes"}`), honoured only on the redis backend (set on sled → startup `warn`, `NoopCoordinator`); fixed 60 s lock TTL + explicit release, no watchdog (full TTL elapses only on a leader crash); a failed leader releases the lock and followers fall back to their own call — **no negative marker, no error caching**, so a non-2xx upstream is never stored (leader still `complete`s so peers stop waiting) and the "never cache a non-2xx" rule is preserved. Any Redis error in any coordinator method degrades to the safe default (`try_lead` → `Leader`, `follow` → `WaitElapsed`, `complete` → ignored), so a coordination outage falls back to exactly today's per-replica behaviour, never a failed request. New metric `zerocache_cross_replica_coalesced_total{provider, kind}` (`kind` ∈ `embedding` | `completion`) — the direct "upstream calls avoided across replicas" count, and the only signal that a peer fill happened. A peer-filled **completion** is a cache hit in every respect: zero `usage`, `X-Zerocache-Completion-Hit: true`. A peer-filled **embedding** reports zero `usage` but is still counted as a **miss** — `X-Zerocache-Hits: 0` / `X-Zerocache-Misses: 1`, and `zerocache_cache_misses_total` increments — exactly how an in-process piggyback is counted (item 21); `{kind="embedding"}` on the new counter is what distinguishes the two. **Deliberately deferred:** multi-item embedding batches; image embeddings; a lock-renewal watchdog; a cross-replica *semantic* index (a separate concern — Project 3 / Deviations item 25). This feature and the semantic tier compose without interaction: `zerocache-http/src/completion.rs::complete()` resolves a request exact-match → semantic near-match (if that tier is enabled) → provider call, and `coalesce_cross_replica` wraps only that final provider call, so an enabled semantic tier simply resolves more requests *before* the coalescing wrapper is reached and a semantic hit returns early without ever entering the cross-replica path — no interaction logic is needed. Tests: `zerocache-ports` +1, `zerocache-http` coalesce module +7 and app/completion +5, config +1, dashboard guard +1; `zerocache-adapters-redis` +9 `#[ignore]`d testcontainers tests — unlike every other `#[ignore]`d Redis test in this repo, these **were** run against a real container in the authoring environment (all 26 of the crate's ignored tests green, coordinator subset run twice for flake). Design: `docs/superpowers/specs/2026-08-29-cross-replica-request-coalescing-design.md`.

29. **Semantic index change-feed push propagation — `XREAD BLOCK` (2026-08-31).** Item 25's "**push propagation … to cut the poll lag**" deferred item. The multi-replica semantic index (item 25, redis only, `--features semantic`) propagated peer writes by polling `changes_since(cursor)` on a `tokio::time::interval` every `ZEROCACHE_SEMANTIC_POLL_MS` (default 2 s), so a peer's vector took up to ~2 s (avg ~1 s) to become searchable and an idle feed still fired an `XRANGE` every tick on every replica. **New port method** `CompletionVectorStore::changes_blocking(cursor: String, timeout: Duration) -> Result<VectorChanges, StoreError>` — like `changes_since(Some(cursor))` but a backend with a native blocking read waits up to `timeout` for the first entry after `cursor` before returning; on timeout it returns empty `upserts`/`deletes` with `cursor: Some(<unchanged>)`. **redis** (`zerocache-adapters-redis/src/vector.rs::xread_blocking`): one `XREAD BLOCK <timeout_ms> COUNT 1000 STREAMS zerocache:semantic:events <cursor>` folded last-op-wins by `exact_key` (shares the hoisted `Slot` enum + new `drain_slots` helper with `xrange_fold`). Runs on a **dedicated** connection off a new `RedisStore.client: redis::Client` field (kept alongside the r2d2 pool) with `set_read_timeout(timeout + 2s)` so the socket never fires before the block — a multi-second blocking read must not occupy a pooled connection or fight `apply_socket_timeouts`' 5 s cap. `XREAD` IDs are exclusive by default, so no `(` prefix; a `"0-0"` cursor returns the whole backlog immediately (no block) one 1000-row page at a time, which is how the boot-time-outage `"0-0"` self-heal path drains. **sled / any feedless backend** returns `VectorChanges::default()` immediately (it never runs the poll loop). **`run_semantic_poll_task`** drops the `tokio::time::interval` ticker entirely and loops on `spawn_blocking(|| vs.changes_blocking(cursor, block))` — the store's own `XREAD BLOCK` is the pacing when the feed is idle; it returns instantly while a backlog remains, so a burst propagates as fast as `spawn_blocking` round-trips allow. A Redis error still keeps the cursor, rate-limited `warn`s (unchanged), and now `tokio::time::sleep(block)` before retry so an outage can't hot-loop `get_connection()` failures. **`ZEROCACHE_SEMANTIC_POLL_MS`** keeps its name, default (2000), and `[250, 60000]` clamp, but now means "max `XREAD BLOCK` duration" — the ceiling on how long a wedged read goes unnoticed and the post-error retry gap, not a fixed poll cadence. **Unchanged:** the query path (local in-memory HNSW KNN, zero network); `apply_vector_changes` and the `zerocache_semantic_index_events_applied_total{op}` metric; the failure posture (no `exit(1)` — reserved for embedder-load failure; `"0-0"` boot cursor still self-heals); `changes_since` and the boot `changes_since(None)` fold, still used for the initial replay + cursor. ## API contract (v2 — multi-tenant, multi-provider)

Endpoint includes the provider in the path, and requires the caller's own provider API key — Zerocache holds no provider credentials of its own:

```text
POST /{provider}/v1/embeddings
Authorization: Bearer <caller's real provider API key>
{ "model": "<real upstream model name>", "input": ["text1", "text2", ...] }

→
{ "object": "list", "data": [ { "embedding": [...], "index": 0 }, ... ], "model": "...", "usage": {...} }
```

`{provider}` is one of `openai`, `mistral`, `gemini`, `huggingface`, `bedrock`, `vertexai`, `azure` (see `decisions.md` for the full reasoning and what's deliberately deferred). The three cloud providers encode routing coordinates into the `model` string itself rather than a new wire field (Deviations item 18):

| `{provider}` | `model` grammar | Example |
| --- | --- | --- |
| `bedrock` | `[<region>/]<modelId>[#<input_type>]` | `us-east-1/cohere.embed-english-v3#search_query` |
| `vertexai` | `[<location>/<project>/]<modelId>[#<task_type>]` | `us-central1/my-proj/text-embedding-005#RETRIEVAL_DOCUMENT` |
| `azure` | `[foundry:]<deployment>[#<input_type>]` | `foundry:cohere-embed-v3-english#document` |

`azure` is only a legal `{provider}` value when `ZEROCACHE_AZURE_OPENAI_BASE_URL` is set — with it unset, `/azure/v1/embeddings` 404s the same way an unknown `{provider}` does. None of the three supports `/{provider}/v1/images/embeddings`; they 404 for the same structural reason `openai`, `mistral`, and `huggingface` do (none implements `ImageEmbeddingProvider`). `input` accepts either a JSON array of strings or a single bare JSON string (matching OpenAI's real, documented `input: string | string[]` contract) — see Deviations item 9 for why this matters more than it looks. Missing/malformed `Authorization` header → `401`. Unknown `{provider}` → `404`. Valid JSON with a missing/wrong-typed required field → `422` (distinct from `400` for JSON that isn't syntactically valid at all — both now come back as the app's own `{"error": "..."}` JSON shape, same as every other error path; see Deviations item 10). The cache is namespaced per-caller: two different callers' identical requests never share a cache entry. Two or more *concurrent* requests that miss on the exact same key within one Zerocache instance are coalesced into a single provider call (Deviations item 11) — this is in-process only, not cross-replica. When `ZEROCACHE_CROSS_REPLICA_COALESCING=1` on the redis backend, a request that resolves to a **single** `CacheKey` (any chat completion; an embedding request with one `input`) is additionally coalesced *across* replicas via a Redis lock. A peer-filled **embedding** reports zero `usage` but still counts as a miss (`X-Zerocache-Hits: 0` / `X-Zerocache-Misses: 1`), exactly like an in-process piggyback; `zerocache_cross_replica_coalesced_total{kind="embedding"}` is what says a peer filled it. (The completion path does return hit headers — see the chat-completions section and Deviations item 26.) Responses also carry `X-Zerocache-Hits` / `X-Zerocache-Misses` headers; `usage` reflects only tokens actually billed for this request's misses (0 for an all-hit batch, 0 for a coalesced request that piggybacked rather than triggering its own provider call, and always 0 for Gemini, which does not report usage at all).

A matching `DELETE /{provider}/v1/embeddings` (same body shape: `{"model": "...", "input": [...]}`, same `Authorization` requirement) removes the cache entries a matching `POST` would have hit, scoped to the caller's own owner_id exactly like every other operation. Response: `{"deleted": <count>}`, where the count is how many keys were requested for deletion, not how many actually existed (deletion is idempotent).

### Image embeddings (2026-07-24)

A parallel endpoint pair, `POST`/`DELETE /{provider}/v1/images/embeddings`, reuses the exact same `EmbeddingsRequest` wire struct and `Authorization: Bearer <key>` requirement as the text endpoints above — only what `input` contains differs:

```text
POST /{provider}/v1/images/embeddings
Authorization: Bearer <caller's real provider API key>
{ "model": "<real upstream model name>", "input": ["data:image/png;base64,<...>", ...] }

→
{ "object": "list", "data": [ { "embedding": [...], "index": 0 }, ... ], "model": "...", "usage": {...} }
```

Each `input` entry is a `data:<mime_type>;base64,<data>` URI, parsed by `zerocache-http/src/image.rs`'s `parse_data_uri` into `zerocache_ports::ImageInput`; a malformed URI → `400`. `{provider}` currently resolves to `gemini` only — the sole entry in `AppState.image_providers` (Deviations item 14) — so `openai`, `mistral`, and `huggingface` (none of which implement `ImageEmbeddingProvider`) all correctly `404` with `{"error": "provider '<name>' does not support image embeddings"}`, the same shape an entirely unknown `{provider}` produces on the text path, just a more specific message. `usage` is always zero, same as Gemini's text path — Gemini never reports usage on any endpoint. Response headers (`X-Zerocache-Hits`/`X-Zerocache-Misses`), the error-shape conventions (Deviations items 9-10), and owner-scoped cache isolation are identical to the text endpoint; request coalescing (Deviations item 11) is not — concurrent misses on the same image are never coalesced (Deviations item 14). `DELETE /{provider}/v1/images/embeddings` mirrors the text `DELETE`: same body shape (`input` as data URIs), same `{"deleted": <count>}` response, same idempotent-count semantics.

### Chat completions (2026-08-28)

```text
POST /{provider}/v1/chat/completions
Authorization: Bearer <caller's real provider API key>
{ "model": "...", "messages": [...], "temperature": 0, ... }   // OpenAI chat shape, forwarded verbatim on a miss

→  the upstream response body, unchanged; 200 on a cache hit
   X-Zerocache-Completion-Hit: true | false

DELETE /{provider}/v1/chat/completions      // same body + Authorization; evicts the entry a matching POST would hit
→  { "deleted": 1 }                          // owner-scoped, idempotent (count is keys requested, not found)
```

`stream: true` is supported: a miss streams the upstream SSE response to the caller live while it is buffered and (on a clean finish) stored; a hit replays the stored completion as SSE (`X-Zerocache-Completion-Hit: true`, `Content-Type: text/event-stream`, ~3 ms between frames). A `stream:true` request that is not cacheable is a pure passthrough. A `stream:true` and `stream:false` request for the same deterministic body share one cache entry. See Deviations item 27.

`{provider}` is any name in the chat-provider registry: the built-ins `openai`, `mistral`, `gemini`, `groq`, `deepseek`, `together`, `openrouter`, `xai`, `fireworks` (each a real hosted OpenAI-wire endpoint, registered with no config), plus any name added or repointed via `ZEROCACHE_CHAT_PROVIDERS="name=url,…"` (self-hosted vLLM/Ollama, an internal gateway). Each configured URL is the prefix up to but not including `/chat/completions`. An unregistered name → `404`. Anthropic's `/v1/messages` surface is now covered (Deviations item 30). `ZEROCACHE_OPENAI_BASE_URL` does **not** affect chat — it is embeddings-only; use `ZEROCACHE_CHAT_PROVIDERS=openai=<prefix>` to repoint the `openai` chat endpoint. See Deviations item 22. Missing/malformed `Authorization` → `401`. A body with no string `model` → `422`. Only **deterministic** requests are cached — `temperature == 0` or an explicit `seed`, and `n` absent/`1`; anything else is a transparent passthrough (forwarded, nothing stored, not counted). The cache key is `owner_id + provider + cache_scope + model + adapter_version + canonicalize_completion_request(body)`, so it's per-caller-namespaced exactly like embeddings, and two requests differing only in `user`/`stream`/`metadata`/key order/number spelling share an entry. A non-2xx upstream response is forwarded with its real status and **not** cached. Concurrent identical misses within one instance are coalesced into one upstream call (in-process only). With `ZEROCACHE_CROSS_REPLICA_COALESCING=1` on the redis backend this extends across replicas (Deviations item 26). Only 2xx responses are stored. A matching `DELETE /{provider}/v1/chat/completions` (same body shape, same `Authorization`, same `401`/`404`/`422` rules) evicts the entry a matching `POST` would have hit — scoped to the caller's own `owner_id`, idempotent, response `{"deleted": 1}`; with the semantic tier enabled it also drops the request's vector record (Deviations item 28). See Deviations item 21 for what's deferred; the semantic tier landed 2026-08-29 (items 24/25), streaming landed 2026-08-30 (item 27).

### Anthropic Messages (2026-09-01)

```text
POST /{provider}/v1/messages
Authorization: Bearer <caller's real Anthropic API key>
{ "model": "...", "messages": [...], "temperature": 0, ... }   // Anthropic request, forwarded verbatim on a miss

→  the upstream response body, unchanged; 200 on a cache hit
   X-Zerocache-Completion-Hit: true | false

DELETE /{provider}/v1/messages      // same body + Authorization; evicts the entry a matching POST would hit
→  { "deleted": 1 }                  // owner-scoped, idempotent (count is keys requested, not found)
```

`{provider}` is currently `anthropic` only (the built-in `anthropic → https://api.anthropic.com`), optionally repointed or added via `ZEROCACHE_MESSAGES_PROVIDERS="name=url,…"` (bare-origin values; adapter appends `/v1/messages` — **not** the chat "full prefix" rule); an unregistered name → `404`. `Authorization: Bearer <key>` is rewritten as `x-api-key: <key>` upstream; `anthropic-version` is forwarded with a default of `2023-06-01`; `anthropic-beta` is forwarded when present **and folded into the cache key** (so different beta names never share a cache entry, not just different models). Missing/malformed `Authorization` → `401`. A body with no string `model` → `422`. Only **deterministic** requests are cached — **`temperature == 0` only** (Anthropic deprecated `temperature` for post-Opus-4.6 models to `1.0`-only, and has no `seed`/`n` parameters), plus non-empty `messages` and `thinking` absent/`null`/`{"type":"disabled"}`; anything else is a transparent passthrough (forwarded, nothing stored, not counted). The cache key is `owner_id + provider + cache_scope + model + adapter_version + anthropic-beta:<value>* + canonicalize_messages_request(body)` (* `anthropic-beta` field appended only when present), so it's per-caller-namespaced and per-beta-variant-scoped exactly like embeddings and chat completions. A non-2xx upstream response is forwarded with its real status and **not** cached. Concurrent identical misses within one instance are coalesced into one upstream call (in-process only). With `ZEROCACHE_CROSS_REPLICA_COALESCING=1` on the redis backend this extends across replicas (Deviations item 26). Only 2xx responses are stored. A matching `DELETE /{provider}/v1/messages` (same body shape, same `Authorization`, same `401`/`404`/`422` rules) evicts the entry a matching `POST` would have hit — scoped to the caller's own `owner_id`, idempotent, response `{"deleted": 1}`. `stream: true` is a raw byte passthrough (not cached, not counted); streaming buffer-and-replay and the `--features semantic` near-match tier for this surface are deferred (Deviations item 30).

### Operational endpoints (unauthenticated, outside the versioned contract)

- `GET /metrics` — Prometheus text format (see Deviations item 5).
- `GET /health` — liveness. Zero I/O; `200 OK` means only "the process and axum router are up," not that the store or any provider is reachable.
- `GET /ready` — readiness. `200 OK` if the configured store backend answers a `get()` on a reserved sentinel key; `503 SERVICE_UNAVAILABLE` on a store-level error. Does not check provider reachability (providers are BYOK and per-request, so there's no single provider connection to probe at startup).
- `GET /dashboard` (+ `/dashboard/*`) — the live savings dashboard, an Astro/React/Recharts single-page app embedded in the binary that polls `/metrics` (see Deviations item 23).

None of these require `Authorization` — they're infrastructure-facing, not part of `/{provider}/v1/embeddings`.

## Multi-consumer design (PRD §7, superseded 2026-07-24 — see `decisions.md`)

PRD §7 originally assumed a single global key space with namespacing/auth deferred until a second consumer needed isolation. That's no longer the current design:

- All consumers go through one running Zerocache process over HTTP — they never touch the store directly. Store concurrency is Zerocache's problem to solve once.
- Cache key is content-addressed AND owner-scoped (`owner_id + provider + model_id + model_version + text`). Two callers embedding identical text under the same model and same forwarded key share a hit for free (the "overlapping corpora across projects" benefit PRD §2 names); two different callers never do, by design — see `decisions.md` for why (cost fairness and a cache-timing existence-leak risk in a fully shared cache, once "caller" stopped being one trusted org).
- Auth is no longer deferred: every request requires a real forwarded provider key (`Authorization: Bearer <key>`), which doubles as both the credential Zerocache uses to call upstream and the input to the owner-scoping hash. There is no "trusted network boundary, no auth" mode anymore.

## Non-goals for v1 (do not implement without a scope discussion)

- Live/conversational query embedding caching (deferred — low reuse rate, unproven).
- **Semantic LLM completion caching IS in as of 2026-08-28** — a different thing from the above (that's about caching *embeddings* of live queries; this caches *chat completions*). `POST /{provider}/v1/chat/completions` intercepts, serves a byte-identical deterministic request from a `CompletionStore`, forwards misses upstream. **The exact-match → semantic near-match tier landed 2026-08-29 (Deviations item 24): opt-in (`--features semantic` build + `ZEROCACHE_SEMANTIC=1`), local candle embedder + HNSW + a hard coarse-key-hash gate. It works on both storage backends — sled in-process, or across replicas on redis via a Redis Stream change-feed (Deviations item 25, needs Redis ≥ 6.2).** The native `POST`/`DELETE /{provider}/v1/messages` surface for Anthropic's `/v1/messages` API landed 2026-09-01 (Deviations item 30), exact-match with a `temperature: 0`-only gate. Still deferred: `finish_reason: tool_calls` special handling beyond what match already covers; streaming buffer-and-replay for Anthropic typed-event SSE and the semantic tier for that surface. Streaming (`stream: true`) buffer-and-replay for OpenAI-wire surfaces landed 2026-08-30 (Deviations item 27); a `DELETE /{provider}/v1/chat/completions` landed 2026-08-31 (Deviations item 28). See Deviations items 21, 24, 25, 27, 28, and 30.
- Semantic/fuzzy similarity matching *on the embedding vector* (cosine / ANN nearest-neighbour) — still a non-goal, and a near-pointless one for an embedding cache: finding a near neighbour requires computing the very embedding you're trying to avoid. **Text canonicalization near-match IS in as of 2026-08-28**, though: the cache key hashes `canonicalize_text(text)` (NFC + lowercase + whitespace/quote/dash folding + trailing-sentence-punctuation trim), so inputs differing only in casing/encoding/punctuation share one entry, while the vector stored under it is still a real embedding of the whitespace-`normalize_text`ed original (first miss in the group wins). See `zerocache-core/src/canonicalize.rs` and the `key_texts`/`provider_texts` split in `embed_batch`. `normalize_text` (whitespace-only, feeds the provider) is unchanged.
- Vector quantization/compression — deferred until a real hit-rate number justifies it.
- Multi-provider *failover* (automatic fallback if a provider call fails) — still out of scope. (Multi-*provider support* itself is no longer a non-goal, nor is multi-instance *storage* — see "Deviations" above; `zerocache-adapters-redis`, `-mistral`, `-gemini` all exist. Failover specifically — trying a second provider after the first fails — is a different feature, not built.)
- Any framework-specific SDK/client package in TS or Python — if a consumer needs to install a Zerocache-specific package, the neutrality goal has failed.
